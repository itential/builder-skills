Why spec-driven

Delivery needs an operating model.

Without one
  • Intent stays implicit — "done" lives in someone's head
  • Discovery happens late — the missing adapter shows up mid-build
  • Design and build blur — decisions made inside the canvas
  • "It works" is never proven — a green job isn't evidence
  • Knowledge walks away — the next team starts from zero
With spec-driven development
Lock intent before touching the environment.
Prove the result before calling it done.
Requirements→Feasibility→Design→Build→Test→As-Built
Each stage: one artifact, one approval. Nothing moves forward on an assumption.

Design decision

Pick how each phase runs.

Workflow
The default
Same steps, same result, every run. Used unless another model has a specific reason in this use case.
Repeatable changes, checks and orchestration
Lifecycle Manager
A thing that outlives the run
Stores the instance and runs day-2 actions against it: a port service, a circuit, a network.
Not for one-off tasks such as a backup or a report
Gateway5 service
Code that runs on a gateway
Python, Ansible or OpenTofu defined in YAML and called from a workflow.
When the work is a script, playbook or plan
FlowAI agent
Judgment at runtime
An agent reasons with platform tools. A parent can call child agents; a child is judged by its answer, not its status.
When the path can't be written down in advance

How the choice is made

Feasibility records what the platform already has. Design asks only the questions the spec leaves open, proposes a model for each phase with the reason, and the engineer confirms it.

Agent first, then deterministic

Build and test an agent to find out what the process should be, then turn it into a deterministic workflow spec. Or build the agent as the delivered answer, or go straight to workflows.

Guardrails

Built into every stage, not bolted on.

Approval gates
The engineer decides
The spec, feasibility, design, test plan and as-built record each need an explicit approval before the next stage starts.
Validate first
Zero errors, zero warnings
Every workflow is deeply validated before it is saved. A warning blocks delivery the same way an error does.
Evidence
A green job isn't proof
Each task's own output is checked for embedded errors and empty values, and the values are stated before a run is called successful.
Safe imports
Ask before replacing
Importing over an existing project replaces it. The builder compares the file with the live project and asks before anything is deleted.
No device remediation
Detect, report, push normally
Golden config finds and reports drift. Corrections go through a normal config-push delivery, never an automatic remediation task.
Permissions
The platform stays in charge
Skills act with the configured credentials and never grant themselves access. Customization can narrow the rules but can't weaken a safety rule.

How it runs

A delivery in four steps.

›spec-agent — pick a use case, lock requirements
customer-spec.md approved
›solution-arch-agent — check the platform, design it
feasibility.md + solution-design.md approved
›builder-agent — build and test each component
project delivered, handed to QA
›qa-agent — test plan, live acceptance tests, as-built
test-report.md + as-built.md signed off
