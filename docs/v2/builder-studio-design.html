Design proposal · v2 · draft for review

Builder Studio: spec-driven delivery as a platform app

This proposal takes the builder-skills delivery model (Requirements → Feasibility → Design → Build → Test → As-Built) out of local AI coding tools and runs it as an Itential Platform application. Each use case becomes a long-lived, versioned record that keeps delivering after its first release.

Sources: builder-skills 1.6.7 · iap (FlowAI apps)
Author: Ankit Bhansali · 2026-09-29
Status: proposal

The idea in one paragraph

Today an engineer runs the builder skills in Claude Code, Codex, or Copilot on a laptop. State lives in markdown files, stage progress is a line in use-case-memory.md, and an approval is the engineer saying "approved" in chat. v2 moves that system into the platform it builds for. Builder Studio is a new IAP application that owns each use case's lifecycle: versioned artifacts, structured approval gates, delivered-asset inventory, and a continuous loop that turns drift, failures, and new requirements into change iterations. The agents run on FlowAI, which already exists. Builder Studio is the delivery system of record that directs them.

Why "continuous"

A use case isn't done at As-Built. The approved artifacts become a baseline. Change requests, drift, failing jobs, regression failures, and platform upgrades each open a new iteration. The iteration starts at the stage that fits the change and runs forward to a new baseline. v1 has the re-entry rule in prose ("re-enters at whichever stage fits"), but nothing enforces or records it.

Why inside the platform
  • The platform already has what v1 scrapes over REST: live task catalog, adapters, projects, job results.
  • FlowAI already runs agents, skills, sessions, tools, and model profiles.
  • Work Center already handles human approvals. Operations Manager already handles triggers and schedules.
  • RBAC, audit, and multi-user access come with the platform. .env files and laptops drop out.
What stays the same
  • Six stages, four agent roles, and the same artifacts, with the same names and sections.
  • Human approval at every gate.
  • The asset under test and its test evidence never come from the same agent.
  • The builder-skills repo stays the canonical source of skill content. It's published into the platform.
Design stance. Builder Studio is a thin, stateful orchestrator. It adds no second agent runtime, workflow engine, or approval system. It adds the parts the platform lacks: a delivery domain model (use case, iteration, stage run, artifact revision, gate), rules for continuous re-entry, and a scoped tool surface that makes the agents safe to run unattended.

These facts come from the builder-skills repo: 17 skills, about 9.1k lines of SKILL.md, a 32-rule AGENTS.md, and a 7-principle constitution. The v2 design keeps v1's intent and replaces its conventions with things the app enforces.

What works and must carry over

  • Handoffs happen through artifacts. "Skills pass files, not verbal summaries."
  • Separation of duties between builder and QA.
  • The engineer approves the test plan before anything runs live.
  • A design-only mode, and entry points from existing assets (project-to-spec, flowagent-to-spec, documentation).
  • Circuit breaker: the same class of error twice in a row means stop.
  • When running unattended, "ask the user" becomes "stop and document".
  • Evals: 57 behavioural evals with 185 assertions, trigger evals, and an e2e suite.

What breaks at scale

  • Stage is prose. Stage: in memory.md is checked against which files exist. Several skills don't update it: builder-agent never sets test, and spec-agent and solution-arch don't set theirs.
  • Stage ownership drift. builder-agent still says it produces as-built.md. The constitution and spec-kit-alignment.md list five stages, not six.
  • Approvals aren't recorded. Nothing captures who approved, when, or which version.
  • No iteration history. A second pass overwrites or appends to the same files.
  • Credentials are per folder. Secrets sit in .env and tokens in .auth.json.
  • Platform data goes stale. The cached JSON is "truth" until someone re-pulls it.
  • Nothing happens after delivery. There's no drift check, no scheduled regression, and no change-request object.
Fix these in v1 now. They're cheap, and they make the v2 import clean. (1) Make builder-agent hand off to qa-agent and stop claiming As-Built. (2) Make every stage skill set Stage. (3) Update constitution principle 4 to six stages. (4) Settle on one use-case folder location: use-cases/<name> or the working directory.

Domain model

There are four aggregates, each with its own consistency boundary. UseCase holds the baseline pointer and membership. Iteration holds stage progress and gates. ArtifactRevision is immutable once written. ChangeRequest collects signals. A StageRun belongs to an iteration and links to exactly one FlowAI session at a time.

Invariants

  • A stage can't start until every earlier stage in the iteration is Approved or Waived.
  • A gate decision applies only if the hashes of the revisions under review still match the current drafts. Otherwise it's stale and rejected with a 409.
  • A revision's content never changes. A new version is always a new revision.
  • A baseline changes only through As-Built approval, or through a drift adoption, which is itself an As-Built revision.
  • One running StageRun per iteration. One open iteration per use case unless policy allows more.

Stage ownership of artifact types

  • Requirements: customer-spec, customer-context
  • Feasibility: feasibility, platform snapshot
  • Design: solution-design sections A–F, diagrams
  • Build: build log, component inventory (§D ids), project
  • Test: test-plan, test-cases, test-report (with re-runs)
  • As-Built: as-built, design As-Built section, spec Amendments
  • Any stage: memory entries (append-only)

Memory, restructured

use-case-memory.md becomes typed, append-only MemoryEntry records: platform-reference, decision, gotcha, test-log, open-item, deviation. Each is tied to the stage run that wrote it. The context tool renders them back to the agent as the same markdown sections, so the skills barely change.

Architecture: where Builder Studio sits

Builder Studio is one backend application and one UI application. Everything else is reused: FlowAI (the agent project, session manager, execution engine, tool registry, tool RPC, and model registry), Work Center, Operations Manager, Automation Studio, and the workflow engine.

new in v2 FlowAI, reused unchanged except the gaps in tab 13 human in the loop platform services

Lifecycle service

Owns the UseCase, Iteration, and ChangeRequest aggregates and the state machines on tab 04. It's the only component that changes lifecycle state. Every transition runs as a command, saved with an optimistic lock, and then an event is published.

Stage runner

Turns "run stage X of iteration Y" into a FlowAI session. It resolves the stage agent, builds the input, calls cogs.AgentSessionManager.startSession, subscribes to session and inference events, enforces the budget and circuit breaker, and cancels the session when a limit is hit.

Gate service

Opens Work Center items for gates and agent questions, stores the hashes of the revisions under review, and applies decisions on workItemComplete. It checks the approver's role and the four-eyes policy.

Artifact store

Holds immutable revisions and their hashes, computes diffs, renders baselines, and exports and imports v1-shaped markdown folders. JSON artifacts such as test-cases.json are checked against schemas that ship with the app.

Builder tools

A set of task:true methods that ToolRegistry registers as method tools. They're the only way stage agents read context or write artifacts. Build-stage writes to the platform go through them too, restricted to the use case's own project and to the initiating user's permissions.

Signal / drift

Takes in signals from topics, schedules, and API calls. It computes asset checksums against the baseline inventory, de-duplicates signals, and opens or updates change requests.

Why not model the pipeline as an IAP workflow? It's tempting: stage = runAgent task, gate = manual task. But a use case lives for months, often has multiple iterations, re-enters at arbitrary stages, sends "request changes" back to a stage, and needs cross-iteration history and baselines. Workflow jobs are the wrong unit for that. v2 keeps lifecycle state in Builder Studio and exposes workflow tasks (startIteration, awaitIteration, raiseSignal), so customers can still embed delivery in their own workflows, such as a ServiceNow change flow.

The continuous loop

After delivery a use case keeps a baseline, and the system watches for reasons to change it. Each reason is a signal. Related signals are grouped into a change request. When someone triages it, it becomes an iteration that starts at the right stage and always runs through Test and As-Built. The result is a new baseline.

Drift detection

  • The baseline stores each delivered component: type, id, name, and a normalized checksum. Volatile fields such as timestamps, lastUpdated, and UI positions are stripped first.
  • A scheduled check runs through an Operations Manager schedule trigger pointed at a BuilderStudio.checkDrift automation. It's per use case or global, hourly by default.
  • Change events are used where they exist. v1 of this design assumes polling, and event-driven checks are an enhancement.
  • The output is a drift signal with a per-component diff.

Scheduled regression

  • test-cases.json gets a new field, repeatable: true|false. Only static and read-only acceptance cases are repeatable by default.
  • Runs go through the same QA tool path (validate, jobs/start, poll) but with no model involved. It's deterministic replay.
  • Results are added to the baseline as evidence. A failure raises a regression signal.

It gets Builder Studio tools that confine writes to the use case's project, carry out the AGENTS.md rules (11, 11a, 11c) in code, and write an audit record for the initiator.
  2. Read-only platform tools, such as the task list, adapters, and workflow details, can be ordinary ToolRegistry tools.

Publishing skills from the repo

  1. skills/ in builder-skills stays canonical. A new generator, scripts/generate-platform-bundle.sh, sits next to the existing vendor-mirror generators.
  2. For each skill, it emits a FlowAI skill (name, description, instructions = SKILL.md body, version = plugin version, approvedTools from a new platform.tools.yaml next to the skill).
  3. The same bundle carries the four stage agent definitions, with their instructions, inputSchema, and tool and skill references.
  4. CI imports it with POST /agent-project-service/project-bundles/import. That needs skills to be part of bundles (gap G1).
  5. Each StageRun records the skill version it used.

What changes inside the skills

  • Auth sections are dropped when running in the platform. The skills check a runtime: platform flag and skip the .env and .auth.json steps.
  • File I/O becomes tool calls. "Write solution-design.md" becomes bs_write_artifact('solution-design', …). Reads go through bs_get_context.
  • curl becomes tools. The REST calls in each skill map to ToolRegistry tools or bs_* tools. The mapping table goes in platform.tools.yaml.
  • "Ask the user" becomes bs_ask_engineer. "Stop and document" becomes a submit with status blocked.
  • Helpers and assets such as helpers/create/*.json and helpers/assets/* are served by bs_get_reference(name). FlowAI skills can't carry files (gap G3).

Customization layers → policies

v1's seven markdown layers map to Policy documents at the org, team, and use-case scope. Each is a set of ADD and OVERRIDE rules, written in markdown and stored with a version. bs_get_context merges them with the same precedence as v1: use case over team over org over core. The context shows the merged rules and where each came from, so the v1 check ("Which customization files are you applying?") still works. Each StageRun pins the policy versions it used. Policies also carry settings the app enforces itself: gate approver groups, the four-eyes rule, waivers allowed, budgets, and whether a stage starts automatically.

Evals move with the skills

The behavioural evals in evals.json run against the platform-published agents in a staging IAP. A harness starts sessions with fixed contexts and checks the artifacts they write. Trigger evals matter less, because in the platform the stage decides which agent runs. The evals/e2e suite becomes the release gate for the builder tools themselves.

This follows how IAP apps are already built. The pattern matches work-center-service: TypeScript, NestJS with @itential/nestjs-platform, hexagonal layout, and pronghorn.json generated from @PlatformMethod decorators. Security & governance

v1 relied on the engineer at the keyboard. v2 runs agents unattended on a shared platform, so the controls have to be enforced in code.

RiskControl in v2
Agent tools run as superuser in FlowAI todayEvery mutating call goes through bs_* tools. They check the StageRun's initiator (read from the StageRun, never from agent input) and confine writes to the use case's project. Read-only tools stay general.
Agent overwrites another project (AGENTS.md 11c, a "destructive full-replace")bs_import_components refuses any _id not in this use case's inventory or project, and never full-replaces an existing project.
QA grades its own workQA's tool allow-list has no build tools, and Build's has no test-report writer. bs_write_artifact enforces stage ownership.
Live test before approvalbs_run_test_case refuses until the plan gate is Approved and the plan hash matches.
Stale or forged approvalGate decisions are tied to revision hashes, go through the Builder Studio API with a role and four-eyes check, and are written to the audit trail.
Runaway cost or loopsPer-stage-run budgets and a circuit breaker, enforced by Builder Studio listening to engine events and cancelling the session.
Secrets leaking into artifactsArtifacts are scanned before storage. There are no .env or .auth.json files, and model credentials stay in ModelRegistry profiles, encrypted with encryptionKey.
Prompt injection from platform data (workflow names, device output)Tool output is treated as data. Write tools are scoped whatever the agent asks for. Destructive actions (delete, full replace) aren't offered as tools.
Skill tamperingSkills are published only by CI with a builder-studio:admin service account. Their version is pinned per StageRun, and the bundle checksum is recorded.

Audit

Each lifecycle command writes auditTrail with the acting user. For agent actions, that's the StageRun initiator. The FlowAI session id is attached so the transcript can be found. Gate decisions, waivers, and drift adoptions are marked as governance events for reporting.

Data residency

Artifacts and memory live in the customer's platform Mongo. Model traffic goes through whatever ModelRegistry profile is bound to the stage. For restricted sites, that can be a gateway-routed model through GatewayManager.llmInvoke, or a local Ollama.

Importing v1 use cases

  1. Upload a zipped use-cases/<name>/ folder, or point at a repo path.
  2. Each deliverable file becomes revision 1 of its type and is marked approved (imported).
  3. use-case-memory.md is parsed. Sections become typed memory entries, Stage is compared with the files present (the files win, as in v1), and Platform References fill projectId.
  4. If an as-built.md exists, baseline v1 is built from §D ids and the live checksums.
  5. .env and .auth.json are ignored. Credentials never cross into the platform.

Keeping both paths

  • An export writes the exact v1 folder shape, so an engineer can keep working locally.
  • A new v1 skill, /builder-studio-sync, could push local revisions into the platform as human-authored revisions. That keeps approvals in one place.
  • The skill content is shared. Only the runtime adapter differs: files and curl locally, bs_* tools in the platform.

Open questions

  1. Q1. Should an approver's inline comments be stored as review threads, like MR comments, or folded into the next context as plain text?
  2. Q2. Does each use case get its own Automation Studio project, as in v1? And who creates it: Builder Studio at the start of Design, or the Build agent?
  3. Q3. Where should large artifacts such as .drawio and big test logs go: GridFS, claim-check, or links out?
  4. Q4. Multi-platform: can one Builder Studio deliver to other platforms (dev, then staging, then prod)? Or does each platform run its own, with promotion by export and import?
  5. Q5. Should the 22 library specs be versioned independently of skills, and should use cases track "upstream spec updated"?
  6. Q6. Model choice per stage: one profile for everything, or a policy-driven profile per stage, such as a stronger model for Design and Build?

Best way to explain this design

  1. Start with the stage strip on Overview and say that nothing about the method changes, only where it runs.
  2. Show the continuous loop diagram next. It's what v1 can't do and the main reason for v2.
  3. Walk flow 1 (run a stage) and flow 3 (gate) on the Runtime flows tab. Together they show that FlowAI does the thinking and Builder Studio does the governing.
  4. Close on flow 4 and the Security tab. Scoped tools are what make unattended agents safe here.
  5. Leave requirements and the app contract for the engineers building it.
